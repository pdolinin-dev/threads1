# Custom Thread Pool

Курсовое задание: собственный пул потоков на Java без использования `ThreadPoolExecutor`.

## Запуск

```bash
mvn compile
mvn exec:java "-Dexec.mainClass=com.Main"
```

В PowerShell аргумент `-Dexec.mainClass=com.Main` нужно оставлять в кавычках.

## Текущая конфигурация демонстрации

В `Main` используется конфигурация:

- `corePoolSize = 2`
- `maxPoolSize = 4`
- `queueSize = 5`
- `keepAliveTime = 5 секунд`
- `minSpareThreads = 1`

Пул стартует с двумя потоками, расширяется до четырех, держит отдельную очередь до 5 задач на worker и завершает лишние потоки после 5 секунд простоя.

## Характеристика реализации

Основной класс — `CustomThreadPool`. Он реализует `CustomExecutor`, который расширяет `Executor` и поддерживает:

- `execute(Runnable command)`
- `submit(Callable<T> callable)`
- `shutdown()`
- `shutdownNow()`

Для каждого worker создается отдельная ограниченная `LinkedBlockingQueue`. Worker выполняет задачи только из своей очереди, поэтому задача заранее закрепляется за конкретным потоком, а не забирается любым свободным worker из общей очереди.

Потоки создаются через `CustomThreadFactory`, получают имена вида `MyPool-worker-N` и логируют создание, выполнение задач, idle timeout и завершение.

`shutdown()` прекращает прием новых задач, но дает уже добавленным задачам выполниться. `shutdownNow()` очищает очереди и прерывает worker-потоки.

## Механизм распределения задач и балансировка

Используется Round Robin по списку активных worker-потоков.

При вызове `execute` пул:

1. Проверяет, что не находится в состоянии `shutdown`.
2. Проверяет число свободных worker. Если их меньше `minSpareThreads`, пытается создать новый worker до `maxPoolSize`.
3. Выбирает worker по счетчику Round Robin.
4. Если в его очереди есть место, добавляет задачу туда.
5. Если очередь заполнена, ищет следующую очередь со свободным местом.
6. Если все очереди заполнены, пытается создать новый worker.
7. Если достигнут `maxPoolSize`, отклоняет задачу.

Round Robin прост, предсказуем и хорошо подходит для демонстрации с похожими по длительности задачами: `normal-task` выполняются около 1200 мс, `overload-task` — около 2500 мс.

Ограничение подхода: при задачах разной длительности одна очередь может стать тяжелее остальных. Для такого случая лучше подошел бы Least Loaded, но здесь выбран Round Robin как более простой и достаточный для заданного сценария.

## Политика отказа

Выбрана политика `Abort`: если все очереди заполнены и число worker уже равно `maxPoolSize`, новая задача отклоняется через `RejectedExecutionException`.

Максимальная емкость текущей конфигурации при перегрузке:

- 4 выполняющиеся задачи;
- 4 очереди по 5 ожидающих задач;
- всего до 24 принятых задач одновременно.

В `Main` в блоке перегрузки отправляется 40 задач. После заполнения потоков и очередей часть задач, примерно с `overload-task-25`, отклоняется, что видно по логам `[Rejected]`.

Плюс политики: пул не копит бесконечную очередь и явно сообщает вызывающему коду о перегрузке. Минус: задача не выполнится, если исключение не обработать. Альтернатива `CallerRuns` могла бы выполнять задачу в вызывающем потоке, но для серверного приложения это риск блокировки потока, который принимает запросы или обслуживает IO.

## Анализ производительности

Пул рассчитан на управляемое поведение под нагрузкой, а не на максимальную производительность. Сильная сторона реализации — изоляция очередей по worker и явный отказ при перегрузке; по логам видно, куда попала задача и какой worker ее выполнил.

По сравнению со стандартным `ThreadPoolExecutor` реализация проще, но менее эффективна:

- `ThreadPoolExecutor` использует хорошо протестированную модель синхронизации и поддерживает разные очереди и политики отказа.
- В стандартном пуле worker обычно конкурируют за общую очередь, поэтому свободный поток быстрее забирает ожидающую задачу.
- В текущей реализации задача закреплена за очередью конкретного worker: это снижает конкуренцию за общую очередь, но может ухудшить баланс при задачах разной длительности.
- Выбор очереди и список worker защищены `synchronized`, поэтому при большом числе коротких задач возможны задержки на входе в `execute`.

Для демонстрационной нагрузки с `Thread.sleep` пул работает эффективно: задачи почти не занимают CPU, а увеличение числа worker с 2 до 4 повышает параллелизм. Для CPU-bound нагрузки `ThreadPoolExecutor`, скорее всего, будет быстрее из-за более зрелой реализации и меньшего объема учебного логирования.

По сравнению с Tomcat или Jetty текущий пул не является полноценным серверным executor:

- нет адаптации под сетевые коннекторы;
- нет встроенных метрик;
- нет интеграции с жизненным циклом сервера;

При этом реализация показывает базовые механизмы серверных пулов включающие в себя ограничение числа потоков, ограничение очереди, освобождение idle-потоков, именование worker и отказ при перегрузке.

## Исследование параметров

Демонстрация использует задачи с искусственной задержкой через `Thread.sleep`, поэтому нагрузка ближе к IO-bound: поток в основном ждет, а не считает на CPU.

В такой модели полезно увеличивать `maxPoolSize` относительно `corePoolSize`. При `corePoolSize = 2` стартуют только две задачи, а `minSpareThreads = 1` заставляет пул заранее расширяться до 3-4 потоков, когда свободных worker не хватает.

Выбранные оказывают следующее влияение:

- `corePoolSize = 2` держит небольшой базовый запас потоков после простоя.
- `maxPoolSize = 4` позволяет пережить короткий всплеск без немедленных отказов.
- `queueSize = 5` ограничивает ожидание и быстро показывает перегрузку.
- `keepAliveTime = 5 секунд` показывает освобождение лишних worker после нормальной нагрузки; в логах появляются `idle timeout, stopping`.
- `minSpareThreads = 1` создает дополнительный worker, когда текущие worker заняты или в их очередях уже есть задачи.

Если уменьшить `queueSize` до 1-2, отказы начнутся раньше, зато принятые задачи будут меньше ждать. Если увеличить `queueSize` до 20, отказов станет меньше, но часть задач будет выполняться заметно позже.

Если уменьшить `keepAliveTime` до 1 секунды, лишние worker будут быстрее завершаться после всплесков, но новые потоки придется создавать чаще. Если увеличить его до 30 секунд, пул быстрее отреагирует на повторный всплеск, но дольше будет удерживать лишние потоки.

Если поставить `minSpareThreads = 0`, пул будет менее активно расширяться и чаще сначала заполнять очереди существующих worker. Если поставить `minSpareThreads = 2` при `maxPoolSize = 4`, пул быстрее выйдет к максимуму потоков, но будет расходовать больше ресурсов при умеренной нагрузке.

Для демонстрации наиболее сбалансирована конфигурация `2/4/5/5s/1`: она показывает нормальное выполнение, динамическое расширение, idle timeout, graceful shutdown и отказ при перегрузке без слишком долгого запуска программы.
