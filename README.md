# Custom Thread Pool

Курсовое задание: собственный пул потоков на Java без использования `ThreadPoolExecutor`.

## Запуск

```bash
mvn compile
mvn exec:java "-Dexec.mainClass=com.Main"
```

В PowerShell аргумент `-Dexec.mainClass=com.Main` нужно оставлять в кавычках.

## Текущая демонстрация

В `Main` используется такая конфигурация:

- `corePoolSize = 2`
- `maxPoolSize = 4`
- `queueSize = 5`
- `keepAliveTime = 5 секунд`
- `minSpareThreads = 1`

Это означает, что пул стартует с двумя базовыми потоками, может расширяться до четырех потоков, у каждого worker-потока есть собственная очередь максимум на 5 задач, а лишние потоки завершаются после 5 секунд простоя.

## Характеристика реализации

Основной класс реализации — `CustomThreadPool`. Он реализует интерфейс `CustomExecutor`, который расширяет `Executor` и поддерживает:

- `execute(Runnable command)`
- `submit(Callable<T> callable)`
- `shutdown()`
- `shutdownNow()`

Для каждого worker создается отдельная `LinkedBlockingQueue` с ограничением `queueSize`. Worker выполняет задачи только из своей очереди. Это отличается от классической схемы с одной общей очередью: задачи заранее закрепляются за конкретным worker, а не забираются любым свободным потоком.

Потоки создаются через `CustomThreadFactory`. Фабрика назначает имена вида `MyPool-worker-N` и логирует создание и завершение потоков. Worker дополнительно логирует выполнение задач, idle timeout и завершение.

При обычном `shutdown()` пул перестает принимать новые задачи, но уже добавленные задачи выполняются до конца. При `shutdownNow()` очереди очищаются, worker-потоки прерываются.

## Механизм распределения задач и балансировка

В текущей реализации используется Round Robin по списку активных worker-потоков.

Когда вызывается `execute`, пул:

1. Проверяет, что пул не находится в состоянии `shutdown`.
2. Проверяет количество свободных worker-потоков. Если свободных меньше `minSpareThreads`, пытается создать новый worker до ограничения `maxPoolSize`.
3. Выбирает worker по счетчику Round Robin.
4. Если у выбранного worker есть место в очереди, задача добавляется туда.
5. Если выбранная очередь заполнена, пул линейно ищет следующую очередь со свободным местом.
6. Если все очереди заполнены, пул пытается создать новый worker.
7. Если достигнут `maxPoolSize`, задача отклоняется.

В демонстрации задачи в основном одинаковые: `normal-task` выполняются примерно 1200 мс, `overload-task` — 2500 мс, поэтому Round Robin дает достаточно равномерную загрузку.

Ограничение выбранного подхода: если одна задача выполняется заметно дольше остальных, очередь этого worker может стать более тяжелой, хотя другие worker уже освободились. Для такого сценария лучше подошел бы Least Loaded, где задача отправляется в самую короткую очередь. В этой работе он не выбран, потому что Round Robin дешевле по накладным расходам и достаточен для заданного сценария.

## Политика отказа

В реализации выбрана политика `Abort`: если все очереди заполнены и число worker-потоков уже равно `maxPoolSize`, новая задача отклоняется через `RejectedExecutionException`.

Для даннрй конфигурации максимальная емкость в момент перегрузки:

- 4 выполняющиеся задачи;
- 4 очереди по 5 ожидающих задач;
- всего до 24 принятых задач одновременно.

В `Main` в блоке перегрузки отправляется 40 задач. После заполнения рабочих потоков и очередей задачи начинают отклоняются, что видно по логам `[Rejected]`.

Преимущества выбранной политики: пул не накапливает бесконечную очередь и не маскирует перегрузку ростом задержек и потребления памяти. Вызывающий код сразу узнает, что система перегружена, и может вернуть ошибку, повторить запрос позже или применить деградацию.

Недостаткаи: задача не будет выполнена, если вызывающий код не обработает исключение. Для некоторых фоновых задач это нежелательно.

## Анализ производительности

Пул рассчитан на управляемое поведение под нагрузкой, а не на максимальную производительность. Его сильная стороной является понятная изоляция очередей по worker-потокам и явный отказ при перегрузке. Это удобно для анализа логов т.к по номеру очереди видно, куда попала задача и какой worker ее выполнил.

По сравнению со стандартным `ThreadPoolExecutor` текущая реализация проще и менее оптимизирована:

- `ThreadPoolExecutor` поддерживает разные типы очередей и политик отказа.
- В стандартном пуле worker-потоки обычно конкурируют за общую очередь, поэтому свободный поток быстрее подхватывает любую ожидающую задачу.
- В текущей реализации задача закреплена за очередью конкретного worker. Это снижает конкуренцию за общую очередь, но может ухудшать баланс при задачах разной длительности.
- В текущем пуле выбор очереди и список worker защищены `synchronized`, поэтому при очень большом числе коротких задач возможны дополнительные задержки на входе в `execute`.

Для демонстрационной нагрузки с `Thread.sleep` текущий пул работает эффективно: задачи не занимают CPU, поэтому увеличение числа worker с 2 до 4 повышает параллелизм и уменьшает ожидание. Для CPU-bound нагрузки стандартный `ThreadPoolExecutor` почти наверняка будет быстрее из-за более зрелой реализации и меньшего количества учебного логирования.

По сравнению с Tomcat или Jetty текущий пул не является полноценным серверным executor:

- нет адаптации под сетевые коннекторы;
- нет встроенных метрик;
- нет интеграции с жизненным циклом сервера;
- нет тонкой настройки обработки очередей под HTTP-нагрузку.

Однако выбранная реализация показывает базовые механизмы, которые есть и в серверных пулах: ограничение числа потоков, ограничение очереди, освобождение idle-потоков, именование worker и отказ при перегрузке.

## Мини-исследование параметров

Для текущей демонстрации использованы задачи с искусственной задержкой через `Thread.sleep`, то есть нагрузка ближе к IO-bound: поток большую часть времени ждет, а не считает на CPU.

В такой модели лучшие результаты дает увеличение `maxPoolSize` относительно `corePoolSize`. При `corePoolSize = 2` одновременно стартуют только две задачи. Когда `minSpareThreads = 1`, пул видит, что свободных потоков не хватает, и заранее расширяется до 3-4 потоков. Поэтому задачи из первой пачки выполняются быстрее, чем при фиксированных двух потоках.

Выбранные значения дают такой эффект:

- `corePoolSize = 2` держит небольшой базовый запас потоков даже после простоя.
- `maxPoolSize = 4` позволяет пережить короткий всплеск без немедленных отказов.
- `queueSize = 5` ограничивает ожидание: очередь достаточно большая для небольшой пачки задач, но быстро показывает перегрузку в блоке `overload`.
- `keepAliveTime = 5 секунд` дает увидеть освобождение лишних worker после нормальной нагрузки. В логах появляются сообщения `idle timeout, stopping`.
- `minSpareThreads = 1` заставляет пул создавать дополнительный worker, когда все текущие worker заняты или в их очередях уже есть задачи.

Если уменьшить `queueSize` до 1-2, отказы начнутся раньше, зато принятые задачи будут меньше ждать в очереди. Если увеличить `queueSize` до 20, отказов в демонстрации станет меньше, но часть задач будет выполняться значительно позже, потому что они будут долго лежать в очередях.

Если уменьшить `keepAliveTime` до 1 секунды, лишние worker будут быстро завершаться после каждого короткого всплеска. Это экономит ресурсы в простое, но при повторяющейся нагрузке приведет к частому созданию новых потоков. Если увеличить `keepAliveTime` до 30 секунд, пул будет быстрее реагировать на повторный всплеск, но дольше удержит лишние потоки.

Если поставить `minSpareThreads = 0`, пул будет менее активно расширяться и чаще сначала заполнять очереди существующих worker. Если поставить `minSpareThreads = 2` при `maxPoolSize = 4`, пул быстрее выйдет к максимуму потоков, но будет расходовать больше ресурсов даже при умеренной нагрузке.

Для выбранной демонстрации наиболее сбалансированная конфигурация — `2/4/5/5s/1`: она показывает нормальное выполнение, динамическое расширение, idle timeout, graceful shutdown и отказ при перегрузке без слишком длинного времени запуска программы.
