# Custom Thread Pool

Курсовое задание: собственный пул потоков с настраиваемыми параметрами, несколькими очередями, логированием, политикой отказа и демонстрационной программой.

## Запуск

```bash
mvn compile
mvn exec:java "-Dexec.mainClass=com.Main"
```

Если `exec-maven-plugin` недоступен, можно запустить из IDE класс `com.Main`.

## Реализованные требования

- `CustomExecutor` расширяет `Executor` и содержит методы `execute`, `submit`, `shutdown`, `shutdownNow`.
- `CustomThreadPool` принимает `corePoolSize`, `maxPoolSize`, `keepAliveTime`, `timeUnit`, `queueSize`, `minSpareThreads`.
- Для каждого worker-потока создается собственная ограниченная `BlockingQueue`.
- Задачи распределяются по очередям в режиме Round Robin. Если выбранная очередь заполнена, пул ищет следующую очередь со свободным местом.
- Если свободных потоков меньше `minSpareThreads`, пул создает новый worker, пока не достигнут `maxPoolSize`.
- Worker завершает работу после `keepAliveTime` простоя, если текущее число потоков больше `corePoolSize`.
- `shutdown()` прекращает прием новых задач и дает уже принятым задачам завершиться.
- `shutdownNow()` прекращает прием задач, очищает очереди и прерывает worker-потоки.
- Логи фиксируют создание и завершение потоков, постановку задач в очереди, выполнение задач, idle timeout и отказы.

## Политика отказа

Выбрана политика `Abort`: при переполнении всех очередей и достижении `maxPoolSize` новая задача отклоняется через `RejectedExecutionException`.

Причина выбора: для серверного приложения под высокой нагрузкой лучше явно отказать лишней задаче, чем бесконтрольно увеличивать задержки, память и число ожидающих запросов. Такой подход дает backpressure вызывающей стороне: клиент или верхний слой может повторить запрос позже, вернуть HTTP 429/503 или применить собственную деградацию.

Недостатки: часть задач теряется, если вызывающий код не умеет повторять запросы или корректно обрабатывать отказ. Для фоновых задач иногда лучше использовать `CallerRuns`, но в серверном обработчике запросов это может заблокировать важный IO/event-loop поток.

## Балансировка

В пуле используется несколько очередей, по одной на worker. При добавлении задачи счетчик Round Robin выбирает следующий worker. Если его очередь заполнена, выполняется линейный поиск следующей очереди со свободной емкостью. Если свободной очереди нет, пул пытается создать новый worker до `maxPoolSize`; если это невозможно, задача отклоняется.

Плюсы Round Robin: простота, малая стоимость выбора очереди, равномерное распределение при похожей длительности задач. Минусы: если задачи сильно отличаются по времени выполнения, одна очередь может стать тяжелее остальных. В таком случае Least Loaded может быть эффективнее, но требует чаще обходить все очереди и измерять их состояние.

## Анализ производительности

Стандартный `ThreadPoolExecutor` обычно быстрее и надежнее для промышленного использования: он давно оптимизирован, покрыт большим количеством сценариев и поддерживает разные очереди, политики отказа, хуки и мониторинг. Реализованный пул полезен как учебная модель и дает больше контроля над распределением задач между конкретными worker-очередями, но уступает стандартной реализации по зрелости и количеству оптимизаций.

По сравнению с пулами Tomcat/Jetty данная реализация проще: в серверных контейнерах есть адаптация под сетевую нагрузку, метрики, интеграция с жизненным циклом сервера и более аккуратная работа с очередями. Здесь реализованы только базовые механизмы, достаточные для демонстрации.

## Мини-исследование параметров

Для CPU-bound задач лучшие результаты обычно достигаются при числе активных потоков около количества доступных ядер: `corePoolSize` и `maxPoolSize` не должны сильно превышать `Runtime.getRuntime().availableProcessors()`, иначе возрастает стоимость переключения контекста.

Для IO-bound задач, где потоки часто ждут сеть, диск или внешние сервисы, `maxPoolSize` можно увеличивать. В демонстрации задачи используют `Thread.sleep`, поэтому рост `maxPoolSize` с 2 до 4 уменьшает время ожидания в очередях.

Практические наблюдения по параметрам:

- Маленький `queueSize` быстрее показывает перегрузку и снижает задержки уже принятых задач, но чаще отклоняет новые.
- Большой `queueSize` уменьшает число отказов, но увеличивает tail latency: задача может долго ждать выполнения.
- `minSpareThreads = 1` помогает заранее держать свободный worker и быстрее реагировать на всплески нагрузки.
- Слишком высокий `minSpareThreads` приближает пул к постоянному содержанию `maxPoolSize` потоков и расходует больше ресурсов в простое.
- Малый `keepAliveTime` быстрее освобождает лишние потоки после всплеска, но при частых коротких всплесках вызывает лишние создания потоков.
- Большой `keepAliveTime` уменьшает churn потоков, но дольше удерживает память и системные ресурсы.

Для заданных демонстрационных задач (`sleep` 1-2.5 секунды) сбалансированная конфигурация: `corePoolSize=2`, `maxPoolSize=4`, `queueSize=5`, `keepAliveTime=5 секунд`, `minSpareThreads=1`. Она показывает нормальную обработку, рост числа потоков при нагрузке, отказ при перегрузке и завершение лишних worker по idle timeout.
